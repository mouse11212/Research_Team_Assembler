# 交叉验证机制 (Cross-Validation Mechanism)

## 概述
交叉验证是研究质量保证的核心机制，通过多视角验证确保研究结论的可靠性。

---

## 1. 验证触发条件

### 自动触发
- 研究报告状态从 `draft` 变为 `pending_review`
- 涉及跨领域概念
- 研究假设需要多方验证
- 证据链需要独立核查

### 手动触发
- 协调员主动分配验证任务
- 研究者请求同行评审
- 发现潜在问题需要核查

---

## 2. 验证任务分配

```yaml
validationTask:
  id: "VT-{timestamp}"
  targetDocument: "{文档路径}"

  validators:
    - agentId: "{验证者ID}"
      focusArea: "{验证焦点}"
      deadline: "{截止时间}"

  validationCriteria:
    - criterion: "逻辑一致性"
      weight: 0.3
    - criterion: "证据充分性"
      weight: 0.3
    - criterion: "跨领域一致性"
      weight: 0.2
    - criterion: "方法论规范性"
      weight: 0.2
```

## 3. 验证执行流程

```
┌─────────────────────────────────────────────────────────────┐
│                    交叉验证流程                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────┐                                              │
│  │ 接收任务  │                                              │
│  └────┬─────┘                                              │
│       │                                                     │
│       v                                                     │
│  ┌──────────┐    ┌──────────────────────────────────────┐  │
│  │ 阅读文档  │ -> │ 检查项:                              │  │
│  └────┬─────┘    │ - 逻辑链条是否完整                    │  │
│       │          │ - 证据是否充分                        │  │
│       │          │ - 结论是否由证据支撑                  │  │
│       │          │ - 方法论应用是否正确                  │  │
│       │          └──────────────────────────────────────┘  │
│       v                                                     │
│  ┌──────────┐                                              │
│  │ 填写验证表│                                              │
│  └────┬─────┘                                              │
│       │                                                     │
│       v                                                     │
│  ┌──────────────────────────────────────────────────────┐  │
│  │              验证结果判断                              │  │
│  ├──────────────────────────────────────────────────────┤  │
│  │  ✅ 通过 -> 状态更新为 confirmed                       │  │
│  │  ⚠️ 有问题 -> 状态更新为 revision + 问题清单           │  │
│  │  ❌ 有分歧 -> 状态更新为 divergent + 分歧记录          │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 4. 验证报告模板

```markdown
# 交叉验证报告

## 验证信息
- 验证ID：{validationId}
- 验证日期：{date}
- 验证者：{validator}
- 被验证文档：{document}

## 验证结果

### 评分汇总
| 验证维度 | 得分 | 权重 | 加权得分 |
|---------|------|------|---------|
| 逻辑一致性 | {score}/10 | 0.3 | {weighted} |
| 证据充分性 | {score}/10 | 0.3 | {weighted} |
| 跨领域一致性 | {score}/10 | 0.2 | {weighted} |
| 方法论规范性 | {score}/10 | 0.2 | {weighted} |
| **总分** | - | - | {total}/10 |

### 验证结论
- [ ] ✅ 通过 - 无需修改
- [ ] ⚠️ 需修改 - 存在可改进之处
- [ ] ❌ 有分歧 - 存在根本性分歧

## 详细评价

### 优点
1. {strength1}
2. {strength2}

### 问题清单
| 序号 | 问题描述 | 严重程度 | 建议修改 |
|------|---------|---------|---------|
| 1 | {issue} | 高/中/低 | {suggestion} |

### 分歧记录（如有）
| 分歧点 | 文档观点 | 验证者观点 | 建议处理方式 |
|--------|---------|-----------|-------------|
| {point} | {view1} | {view2} | {suggestion} |

## 后续建议
{suggestions}
```

---

## 5. 分歧记录格式

```yaml
divergenceRecord:
  id: "DR-{timestamp}"
  document: "{文档路径}"
  discoveredAt: "{timestamp}"

  divergencePoints:
    - point: "{分歧点描述}"
      documentView: "{文档中的观点}"
      validatorView: "{验证者的观点}"
      evidenceComparison:
        documentEvidence: "{文档提供的证据}"
        validatorEvidence: "{验证者提供的证据}"

  suggestedResolution:
    - option: "{解决方案1}"
      pros: "{优点}"
      cons: "{缺点}"
    - option: "{解决方案2}"
      pros: "{优点}"
      cons: "{缺点}"

  status: "pending_resolution"
```

---

## 6. 验证结果处理

| 验证结果 | 状态变更 | 后续动作 |
|---------|---------|---------|
| ✅ 通过 | `under_review` → `confirmed` | 进入下一研究阶段 |
| ⚠️ 需修改 | `under_review` → `revision` | 返回原作者修改 |
| ❌ 有分歧 | `under_review` → `divergent` | 触发冲突复盘流程 |
